# Moteur Rust expérimental

[English](en/rust-runtime.md)

Les exécutions Rust interrompues sont enregistrées dans un journal privé `goal-recovery.json`, dans le dossier de données de Studio, avant l'admission du prompt. Après un redémarrage, Studio tente une fois chaque reprise admissible, après avoir revérifié la session, le projet, l'objectif, le budget et la file inactive. Il envoie une continuation de service visible, sans rejouer le prompt utilisateur ni parcourir les anciens objectifs actifs. Les exécutions arrêtées ou terminées, les projets supprimés, les sessions archivées ou enfants, les objectifs effacés, inactifs ou épuisés sont exclus. Les réglages actuels du modèle et du raisonnement prévalent sur le journal. L'arrêt attend les écritures de métadonnées ; un journal illisible bloque la reprise sans être remplacé. Cette fonction concerne seulement le moteur Rust optionnel et ne réinitialise pas les compteurs ni les autorisations.

La création native peut confirmer une grande session avant de restaurer son objectif. La reprise attend au maximum 30 secondes la fin de cet état vide provisoire, puis revérifie l'identité et l'admissibilité juste avant le prompt. Un objectif modifié ou une session occupée est refusé. La commande `node --test test/goal-recovery.test.mjs test/server-goal-recovery.test.mjs test/rust-goal-recovery.test.mjs` couvre ces contrôles. `node scripts/rust-recovery-canary.mjs ABSOLUTE_BINARY_PATH` vérifie la restauration de 4 000 entrées synthétiques avec un vrai démon isolé, intercepte le prompt avant l'inférence et confirme la conservation des compteurs. Ce contrôle ne prouve pas l'achèvement d'un tour de modèle.

Studio conserve le moteur JavaScript par défaut. Pour essayer Rust, définissez `PRIME_STUDIO_RUST_CLI` avec le chemin absolu d'un exécutable officiel Prime Agent 0.10. Studio démarre son propre démon dans un espace privé ; il ne se connecte jamais à un démon utilisateur existant. Cette option n'est pas activée par l'installateur de bureau.

Gardez `PRIME_AGENT_CLI` dirigé vers un paquet JavaScript compatible. L'archive npm officielle 0.10 en contient un dans `legacy/prime-agent/dist/bundle/cli.js` ; ce paquet imbriqué annonce la version 0.9.8. Installez ses dépendances dans ce paquet avec `npm install --ignore-scripts`. Le dossier `dist` à la racine contient des lanceurs, pas les modules de métadonnées. Studio utilise le paquet JavaScript pour les modèles et les réglages ; Rust exécute les tours de l'agent.

Pour un premier essai, utilisez des dossiers dédiés pour `PRIME_AGENT_CODING_AGENT_DIR` et `PRIME_AGENT_SESSION_DIR`. Rust gère ses fichiers de session natifs. Une reprise exige le fichier exact et une réponse confirmant la même session et le même projet. Ne faites pas travailler deux moteurs simultanément dans le même dossier de sessions. L'adaptateur vérifie le socket privé, le superviseur et les identités de session. Une mutation dont le résultat est incertain n'est jamais répétée automatiquement.

L'intégration Rust couvre certaines fonctions de Studio, sans garantir la parité avec les extensions JavaScript. Le tableau décrit le chemin Rust actuel : la présence d'un fichier ou d'une extension dans le dépôt ne prouve pas que Rust le charge ni qu'il se comporte de la même façon.

| Fonction | Comportement et limite du mode Rust |
| --- | --- |
| Questions, connaissances du projet, Roadmap | Pont Studio `python_repl` authentifié et limité, initialisé à chaque tour. La propriété Roadmap d'un appel enfant n'est pas garantie si le noyau natif ne fournit pas son véritable identifiant de session. |
| Computer Use | Refusé par le chemin d'exécution et l'API Rust ; utiliser le moteur JavaScript pour cette fonction. |
| Fournisseurs Meta et Muse-Code | Le fournisseur Meta JavaScript de Studio est explicitement refusé. L'extension OAuth Muse-Code JavaScript n'est pas chargée par le moteur Rust ; seuls les modèles annoncés par l'exécutable natif entrent dans son catalogue. Aucune parité fournisseur n'est revendiquée. |
| Extension de contexte | Le hook JavaScript `studio-context` n'est pas chargé. Rust ajoute sa propre instruction d'affichage des images du projet ; cela ne prouve pas l'équivalence du hook de contexte. |
| Images et fichiers | Les images peuvent être envoyées dans les prompts natifs. Les pièces jointes ordinaires de Studio sont refusées avant la création de session. Les images du projet s'affichent depuis leur chemin relatif d'origine ; les fichiers supprimés ne sont pas archivés. |
| Catalogue et préférences | La liste de l'exécutable natif fait autorité ; les métadonnées JavaScript enrichissent uniquement les identifiants correspondants. Une liste native invalide ou indisponible bloque le catalogue. À la création, Studio transmet le modèle et le niveau de raisonnement choisis. L'adaptateur de session active n'expose pas de changement de modèle ; il envoie `set_thinking_level` uniquement si le démon annonce `session_scoped_preferences`. La version 0.10 ne l'annonce pas : Studio refuse donc la demande avant d'envoyer la commande et ne peut pas modifier les préférences globales par ce chemin. Le `main` actuel de l'amont possède les commandes natives `/model` et `/effort` limitées à une session, mais l'adaptateur Studio n'expose pas encore ces deux commandes comme choix en direct. |
| RPC, headless, quiescence, noyau et flux du démon | Rust utilise son protocole natif, son pont `python_repl` et `wait_for_headless_completion` avec la barrière de quiescence RLM. L'exécutable Rust ne charge pas les hooks JavaScript de loader, RPC, headless, noyau ou flux du démon. Les tests Rust couvrent des chemins sélectionnés, pas la parité de bout en bout avec ces hooks. |

Le moteur JavaScript reste le choix par défaut ; son comportement et ses extensions ne changent pas lorsque l'option Rust est désactivée.

Les modèles et niveaux de raisonnement choisis pour les sous-agents Studio sont refusés avant la création d'une session Rust. Rust possède ses propres sous-agents natifs, mais la politique JavaScript de Studio ne leur est pas appliquée. Cette option expérimentale ne garantit pas le fonctionnement de toutes les extensions JavaScript.

Exécutez `node --test test/rust-*.test.mjs` pour vérifier le protocole, le moteur et le pont Python. `node scripts/rust-native-canary.mjs CHEMIN_ABSOLU_EXECUTABLE` utilise un état temporaire isolé et `--offline` pour tester un vrai démon : connexion, création, attachement, lecture et fermeture de la session, sans appel à un modèle. N'utilisez pas de données ou d'identifiants de production pour ce test.

L'exécutable officiel Windows 0.10 a passé les vérifications de connexion et de première session, mais notre test de réouverture à froid a échoué : l'ancien worker détenait encore son bail après le succès annoncé par `complete_owned_session`. Le `main` actuel de l'amont comprend une récupération des baux adaptée à Windows et un test de réouverture à froid qui attend la fin de l'ancien worker et la libération de son bail. Cette prise en charge en amont ne prouve pas que cette intégration Studio réessaie sans risque ni que son candidat actuel réussit un nouveau test Windows à froid : aucune preuve récente de ce type n'est fournie ici. Ne supposez pas que la session s'ouvre dès l'arrêt du superviseur ; conservez la même session sauvegardée et affichez son état de récupération pendant la libération du bail. Les tests Linux en boucle locale et les canaris de protocole ne prouvent ni l'accès à un vrai fournisseur ni la parité des extensions. Ce mode reste expérimental.
